# Project Status & Roadmap

**For any new session picking this up: read this file first, then update it as you go.** Keep "Working" current, move finished items out of "Next up," and add anything you discover to "Known gaps." This file is for whoever (human or Claude) picks the project up next — it is not user-facing like `README.md`.

## What this is

A SpeedQuizzing-style live quiz app ("Too Quick To Cheat Quizzing"). Node/Express/Socket.IO server + Vite/React client. **Deployed and live at https://2quick2cheat.com** (custom domain on top of Render, which auto-deploys on push to `main` — see "Git repo + Render deployment" below; the original `too-quick-to-cheat.onrender.com` URL still works too). See `README.md` for the full feature/user-facing writeup — this file is the dev-continuity summary instead.

## Design guidelines

- **Host-facing tools are optimized for a Windows PC/laptop (desktop)**: `HostSetup`, `HostRoom` (+ its `AddRoundModal`/`RunningOrderPanel`), `BankManager`, `RoundEditor`, and `PresentationScreen` (the big-screen/projector view the host opens). The quiz master always runs these on a desktop/laptop — design and test these for mouse + keyboard on a normal desktop viewport first; mobile usability is a non-goal (though we still avoid the worst breakage, e.g. horizontal page overflow).
- **Player-facing tools are optimized for mobile**: `PlayerJoin`, `PlayerGame`. Players always join from their phone — design and test these mobile-first (touch targets, portrait layout); desktop usability is a non-goal there.
- `Login`/`Home` are effectively host-only in practice (players never sign in), so treat them as desktop-optimized too.
- When in doubt about which bucket a new screen/component falls into, ask rather than assume — don't retrofit a host tool to be mobile-first or vice versa without checking first.

## Working (built and verified live in-browser)

- **Quiz Bank**: rounds of up to 10 questions, 4 question types (multiple choice, "normal"/letters-board, number, sequence), optional picture attached to any question.
- **Round visibility**: 🌐 public (communal, anyone signed in can edit) or 🔒 private (only visible/editable by its creator). Enforced server-side, not just hidden in the UI.
- **Accounts**: self-service signup gated by a shared `INVITE_CODE`, bcrypt + JWT session cookie, works across both REST and the Socket.IO handshake. Hosting and Quiz Bank management require sign-in; **joining a game as a player never does** (room code + nickname only, by design).
- **Running Order**: the quiz master builds a live, editable queue of rounds (each with its own chosen round type) — buildable while players join, editable mid-game, nothing locked until that round actually starts.
- **Round types** (chosen per queue entry, independent of the round's content): Standard (5 pts + speed bonus to top 5), Speed (5 pts to everyone correct, +5 bonus only to the single fastest), Evil (wrong costs 5 pts, skipping is safe), Go Wide (half points for a wider shot — mechanic is type-specific, see below).
- **Fixed: Go Wide did nothing for Number/Sequence questions**: previously `goWide` in `submitAnswer()` only ever turned on for `multiple_choice`/`normal` — Number and Sequence questions in a Go Wide round silently scored as if it were a Standard round (full points, no actual "going wide" mechanic available at all). User caught this by testing a Go Wide round with both types. Added a *per-answer opt-in* mechanic (not the forced-always-pick-2 pattern MC/Normal uses, since the user explicitly asked for a "button" the player chooses to press) — distinct from MC/Normal, which were working correctly and weren't touched: **Number** gets an optional "🎯 Go Wide (±1, half points)" toggle above the keypad (`PlayerGame.jsx`'s `wideNumber` state) — submits `{ number, wide }`, and `gameManager.js` accepts the number 1 above/below the exact answer when `wide` is set. **Sequence** gets a ⚡ wildcard-toggle button next to every item, in both the pool and the player's chosen order (`wideSkipIndex` state, one at a time) — submits `{ order, wideSkipIndex }`, and a new `arraysEqualIgnoring()` helper strips that one item's position from both the submitted and correct order before comparing, so only the relative order of everything else has to match. Either mechanic halves the question's points when used (`usedGoWide` flag, replacing the old type-gated `goWide` flag for the halving decision), same as MC/Normal's forced halving — matches if not used, full points as normal. The player-reveal rewrite from the previous session got this wrong in two places: it treated each element of `correctOrder` as an `originalIndex` *number* and tried `board.items.find((it) => it.originalIndex === originalIndex)` to look up display text — but comparing a string to a number with `===` is always `false`, so the lookup returned `undefined` for every item, on *every* sequence reveal, Go Wide or not. This is almost certainly why Go Wide on Sequence looked broken too (reported in the same message) — the scoring itself is unit-tested and unchanged, but there was no way to see whether a wildcarded answer judged correctly through a reveal screen rendering blank text. Fixed both spots (the question-bar `correctAnswerText` and the reveal-phase board itself) to use `reveal.correctOrder`'s elements directly as display text, matching the working `HostRoom`/`PresentationScreen` pattern. **Verified**: build is clean; confirmed correct by direct comparison against the already-correct host/presentation code doing the identical `.join(" → ")` — did not re-run a full live timed click-through (same browser-automation-vs-countdown-timer limitation as before). Go Wide for Number is a separate, still-open question — see "Known gaps" above.

## Known gaps (not yet fixed, flagged along the way)

- **Reload mid-question (players only — host is now fixed, see below)**: if a *player* reloads during a live question (not between questions), they land back on the "lobby" phase until the *next* phase-change event arrives — they don't get shown the current question. Deferred, not forgotten. The presentation screen has the same gap (`spectator:join` doesn't send current phase either), lower priority since it self-heals the moment the host's next action broadcasts a new phase event.
- **Go Wide for Number reported still not working on a real device** — the Sequence half of this is now root-caused and fixed (see "Fixed: Sequence reveal..." below); Number's status is still unconfirmed since the user's reports so far have specifically called out Sequence. `gameManager.js`'s scoring logic (both types) is unit-tested and re-verified against the live code with no regressions. Worth re-testing Number specifically now that the Sequence reveal bug (which plausibly made Go Wide *look* broken even when scoring was fine underneath) is fixed.
- **No automated tests.**
- **No Quiz Bank export/import** — no way to back up or share your rounds as a file yet.
- **Orphaned uploads**: deleting a question/round doesn't delete its uploaded picture from `server/data/uploads/`.
- **Legacy rounds have `ownerId: null`**: the two original sample rounds predate accounts, so nobody "owns" them — they're public and can't be made private without recreating them.
- **Game state is in-memory only**: a server crash or redeploy loses any in-progress game (not the Quiz Bank — that's on disk). Acceptable for a hobby project; would need Redis or similar to fix properly.
- **Found and fixed while building the bank table**: `#root` in `index.css` had no `width` set. It's body's flex item (body is `display:flex; justify-content:center`), so with `width:auto` it sized to its content's max-content width instead of the viewport — invisible until a page had genuinely wide unwrappable content (a table, or 4 type-toggle buttons in a row), at which point the *whole page* overflowed horizontally and (because of `justify-content:center`) visibly shifted left/cropped rather than just showing a scrollbar. Fixed by giving `#root` `width: 100%; min-width: 0;`. Also added `overflow-x: hidden` to `body` as a defensive backstop, and `flex-wrap: wrap` to `.type-toggle` (4 buttons in a row had the same latent issue on narrow screens, independent of this bank-table work). If a future page introduces more wide/unwrappable content, this class of bug shouldn't resurface — but worth knowing why `#root` has an explicit width now, since it looks redundant until you know this.
